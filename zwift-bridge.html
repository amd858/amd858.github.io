Zwift BLE Bridge

ESP32-C3 dual-mode firmware · heart rate monitor bridge · real-time telemetry

A sophisticated dual-mode BLE firmware that simultaneously acts as a client (subscribing to a physical heart rate monitor strap) and a server (broadcasting Running Speed & Cadence metrics to Zwift). Runs on a single ESP32-C3 chip with intelligent sensor auto-discovery, non-blocking architecture, and NeoPixel status feedback.

Core Architecture

The firmware breaks into two distinct BLE roles operating concurrently on one chip:

  • BLE Client: Connects to external heart rate monitor (Magene, Garmin, etc.) and subscribes to HR notifications
  • BLE Server: Broadcasts RSC (Running Speed & Cadence) and HR data to Zwift app
  • Loop Model: Non-blocking state machine — no delay() calls; strict 1-second data pipeline intervals
  • Sensor Addressing: Lock mode (bind to specific MAC) or Auto mode (auto-connect to first HR monitor detected)
  • Memory Management: Explicit cleanup of global BLE client pointers to handle unexpected strap disconnection
  • Stability Engine: ESP32 Arduino Core v3.2.0+ with discrete 1-second scanning windows (every 5 seconds) to prevent "scan not active" crashes

Data Formats & Buffers

RSC Measurement Buffer (10 bytes)

Byte 0:   Flags (0x03 = speed, cadence, stride, distance present)
Byte 1-2: Instantaneous Speed (uint16_t, little-endian) — speed in 0.01 m/s units
Byte 3:   Instantaneous Cadence (uint8_t) — steps per minute
Byte 4-5: Stride Length (uint16_t, little-endian) — millimeters
Byte 6-9: Total Distance (uint32_t, little-endian) — meters

Heart Rate Buffer (2 bytes)

Byte 0: Flags (0x00 = 8-bit HR, no RR intervals)
Byte 1: Heart Rate (uint8_t) — BPM (0–255)

Speed Conversion (from UART)

Input Format
Floating-point string via Serial1 (e.g., "12.5")
Scaling
Raw input × 0.125 = km/h (then converted to 0.01 m/s units for BLE)
Validation Range
0–40 km/h (out-of-range values rejected silently)
Example
Treadmill sends "16.0" → 16 × 0.125 = 2 km/h → BLE buffer = 200 (0.01 m/s)

Firmware Subsystems

1. Telemetry Ingestion (handleUartIngestion)

Listens to Serial1 (RX_PIN 6) for incoming speed data. Parses floating-point strings, applies 0.125 scaling factor, validates against 0–40 km/h bounds, and updates simulatedKmph for the RSC pipeline.

2. Sensor Background Scanning (handleSensorBackgroundScanning)

Manages intelligent BLE scanning to detect heart rate monitors without jamming the server's advertising. Executes 1-second scan windows every 5 seconds, leaving 4-second silent periods for uninterrupted Zwift server operations. Prevents ESP32 "scan not active" crash loops.

3. Sensor Binding (connectToPhysicalStrap)

Processes newly discovered HR monitor advertisements. Validates Heart Rate Service UUID (0x180D), enforces MAC address lock if configured, safely destroys stale memory pointers, creates a fresh BLE client handle, and subscribes to HR characteristic notifications via CCCD.

4. Data Pipeline Execution (runDataPipelineExecution)

Runs on a strict 1-second interval. Packages simulatedKmph into RSC GATT buffer format (10 bytes), passes physical or simulated HR into HR buffer (2 bytes), and notifies Zwift of both. Cadence, stride length, and total distance values are maintained as persistent state variables.

5. Zwift Connection State (handleBleConnectionState)

Monitors Zwift app connection/disconnection. On disconnect, wipes data pipelines, resets HR tracking to 0, and restarts server advertising beacon for instant reconnect or app switch.

6. LED Status Updates

Updates NeoPixel (LED_PIN 8) every 250ms based on connection state. Provides visual feedback without requiring serial monitor access.

LED Status Indicators

The onboard WS2812B NeoPixel communicates hardware and connectivity state instantaneously:

Blinking Blue
Scanning for HR monitor (powered on, no strap detected)
Blinking Amber
Strap bound successfully; waiting for Zwift app to pair
Solid Purple
Connected to Zwift but strap is missing; transmitting fallback HR simulation (50–60 BPM)
Solid Green
Perfect operation: Live physical HR and speed data flowing through to Zwift

Configuration Modes

Lock Mode (Bind to Specific Strap)

const String targetMacAddress = "ed:92:5c:9c:06:a2";

Rigidly bind to a specific heart rate monitor MAC address. Useful in busy gym environments to prevent cross-talk with nearby straps. The hub ignores all other HR monitor advertisements and waits exclusively for this device.

Auto Mode (Auto-Discover)

const String targetMacAddress = "";  // Empty string

Automatically connect to the first HR monitor detected in range. Ideal for flexible, single-user setups. The hub scans and binds to whichever device advertises HR Service (0x180D) first.

Debug Output

const bool debugMode = true;

Enable serial debug output at 115200 baud. Shows connection state, HR values, speed conversions, and BLE events. Disable to reduce noise if deploying in production.

Safety & Thresholds

Heart Rate Alert Output

GPIO 3 (WARNING_HEARTRATE_PIN)
Driven HIGH when HR exceeds 114 BPM; useful for triggering an external alarm, warning LED, or relay

Speed Validation

  • Minimum: 0 km/h
  • Maximum: 40 km/h
  • Out-of-range values are silently rejected and do not update the pipeline

Fallback HR Simulation

If Zwift is connected but the physical HR strap is missing, the firmware transmits a safe random simulation pulse (50–60 BPM) so the app doesn't hang or timeout. When the strap reconnects, live data resumes immediately.

Deployment & Installation

Prerequisites

  1. Arduino IDE 2.x or PlatformIO installed
  2. ESP32 Arduino Core v3.2.0 or newer
  3. Adafruit NeoPixel library installed via Library Manager
  4. ESP32-C3 Dev Module board selected in IDE

Hardware Setup

  • Connect USB-C cable to ESP32-C3
  • Verify COM port detected in IDE
  • Connect WS2812B NeoPixel to GPIO 8 (data), GND, and 5V
  • (Optional) Connect UART source to RX_PIN 6 and GND
  • (Optional) Connect relay/alarm to GPIO 3 for HR alert

Firmware Configuration

Before uploading, edit the source file:

// Line ~17: Set your sensor MAC or leave empty for auto-detect
const String targetMacAddress = "";  // or "XX:XX:XX:XX:XX:XX"

Upload & Verification

  • Select Tools → Board → esp32 → ESP32-C3 Dev Module
  • Select correct COM port and upload the sketch
  • Open Serial Monitor at 115200 baud
  • Watch NeoPixel: should blink blue (scanning state)
  • Bring HR strap into range; LED should blink amber when bound
  • Open Zwift app, pair the "SENSOR Hub" device; LED should turn green when live data flows

Testing Checklist

  • ☐ NeoPixel responds to connection state changes (blue → amber → green)
  • ☐ Physical HR monitor pairs and transmits HR values to firmware (verify in Serial Monitor)
  • ☐ Zwift app detects and pairs with "SENSOR Hub" broadcaster
  • ☐ HR and speed metrics display live in Zwift
  • ☐ Pulling HR strap battery triggers purple fallback state (LED solid, Zwift simulation active)
  • ☐ Reattaching strap resumes green state and live data
  • ☐ UART speed input (if used) converts correctly (raw × 0.125 = km/h)
  • ☐ HR alert output (GPIO 3) goes HIGH when HR exceeds 114 BPM
  • ☐ No memory leaks or reboots over 1+ hour runtime
  • ☐ Serial Monitor shows clean debug output; no "scan not active" errors
